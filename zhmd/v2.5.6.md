# v2.5.6 技术文档：AMD/ROCm 兼容性

> 基线提交：`836b488`（v2.5.5）
> 提交：`80582bb`（功能）/ `6f1c2ff`（显示名称门控修复）/ `a484710` + `21f49a8`（README）/ `ed78766`（changelog）

---

## ① 目的

为本自定义节点添加 **AMD/ROCm 兼容性**。nunchaku 仅支持 NVIDIA CUDA，在 AMD/ROCm 系统上无法导入，
此前会导致所有依赖 nunchaku 的节点虽然注册成功、但运行时直接崩溃（执行工作流时出现晦涩的
`ImportError`）。本版本让包在启动时检测 nunchaku 缺失并自动适配：

- **禁用** AMD/ROCm 上所有依赖 nunchaku 的节点（不注册，因此完全不会出现在节点列表中）。
- **保留** 不依赖 nunchaku 的 Krea2 ControlNet 节点，在所有平台上功能完整
  （`Krea2ControlNetLoraLoader` 以及 `NunchakuQI&ZITDiffsynthControlnet` 的 Krea2 路由）。
- **防护** 所有运行时 nunchaku 导入，旧工作流会收到清晰的 `RuntimeError`
  （"nunchaku is required..."），而不是晦涩的 `ImportError`。

实现方式与姊妹仓库 `ComfyUI-NunchakuFluxLoraStacker` 中已验证的方案（0xDELUXA 的 PR #6
及其后续修复）保持一致，并根据本包的模块布局进行了适配。

### 要求

1. **NVIDIA 上无回归**：存在 nunchaku 时，9 个节点必须全部注册，行为与之前完全一致。
2. **AMD 上互斥**：依赖 nunchaku 的节点禁用，不依赖的（Krea2）节点可用。
3. **清晰的错误**：运行时 nunchaku 导入抛出描述明确的 `RuntimeError`，绝不抛出裸 `ImportError`。
4. **加载器不动**：`Krea2ControlNetLoraLoader` 与 ControlNet 节点不受本次变更影响。

## ④ 代码详细解说

### 4.0 整体架构

```
ComfyUI 启动
      │
      ▼
__init__.py: _NUNCHAKU_AVAILABLE 探测
      │  try: import nunchaku  → True（NVIDIA）
      │  except ImportError    → False（AMD/ROCm）
      ▼
if _NUNCHAKU_AVAILABLE:
    注册 QwenImage / Z-ImageTurbo 节点（7 个）      ← 仅 NVIDIA
else:
    跳过（警告 "[ROCm/AMD] nunchaku is not available..."）

始终注册：
    Krea2ControlNetLoraLoader                         ← 不依赖 nunchaku
    NunchakuQwenImageDiffsynthControlnet              ← 不依赖 nunchaku
```

### 4.1 `__init__.py` — 可用性探测与注册门控

**探测**（模块级，在任何节点导入之前）：
```python
try:
    import nunchaku  # noqa: F401
    _NUNCHAKU_AVAILABLE = True
except ImportError:
    _NUNCHAKU_AVAILABLE = False
    logger.warning("[ROCm/AMD] nunchaku is not available...")
```
在 AMD 上 `import nunchaku` 会抛出 `ImportError`（该包只随附 CUDA 专用二进制），
因此启动时恰好一次将标志翻转为 `False`。

**注册门控**：原先单一的 `try: from .nodes.lora.qwenimage import ...` 块（一次性注册全部
节点）被拆分为两部分：

1. `if _NUNCHAKU_AVAILABLE:` — 导入并注册 7 个依赖 nunchaku 的节点类
   （`NunchakuQwenImageLoraLoader/Stack`、`V1`/`V2`/`V3`、
   `NunchakuZImageTurboLoraStackV1`/`V4`）。
2. 无条件块 — 注册 `Krea2ControlNetLoraLoader`。

ControlNet 节点（`NunchakuQwenImageDiffsynthControlnet`）保留其独立的 `try` 块；
其 Krea2 路由只做类型判断（`_classify_controlnet_target`），从不导入 nunchaku，
因此在 AMD 上可用。

**显示名称门控**：`NODE_DISPLAY_NAME_MAPPINGS` 中两条硬编码条目现在用
`**({} if not _NUNCHAKU_AVAILABLE else {...})` 防护，AMD 上永远不会暴露
未注册节点的显示名称（避免 ComfyUI 报告不匹配）。

### 4.2 `nunchaku_code/lora_qwen.py` — 保持模块可导入

该模块会被所有 Qwen/Z-Image 节点在运行时导入（`from nunchaku_code.lora_qwen import ...`）。
其顶层的 `from nunchaku.lora.flux...` 导入在 AMD 上会抛 `ImportError`，这会让
仅仅导入该模块的无关代码路径也崩溃。防护逻辑：

- 成功时：`_NUNCHAKU_AVAILABLE = True`，名称正常绑定。
- 失败时：`_NUNCHAKU_AVAILABLE = False`，三个转换器助手
  （`pack_lowrank_weight`、`reorder_adanorm_lora_up`、`unpack_lowrank_weight`）
  绑定为 `_nunchaku_required`（抛出描述明确的 `RuntimeError`）。
  模块本身导入成功，因此 `_load_lora_state_dict` 等检查路径仍可使用。

### 4.3 `wrappers/*.py` — 在包装层使用相同防护

`wrappers/qwenimage.py`、`wrappers/qwenimage_v2.py`、`wrappers/zimageturbo.py`
由节点代码通过 `importlib` 惰性加载。每个文件现在都用 `try/except ImportError`
包裹顶层 nunchaku 导入，失败时设置 `_NUNCHAKU_AVAILABLE` 并把
`compose_loras_v2` / `reset_lora_v2` 替换为抛 `RuntimeError` 的函数。
这样 `spec.loader.exec_module(wrappers_module)` 在 AMD 上不会因 `ImportError` 崩溃。

### 4.4 `nodes/lora/qwenimage*.py` — 运行时导入防护

所有在运行时导入 `nunchaku` 或 `nunchaku_code.lora_qwen` 的位置都被包裹：

```python
try:
    from nunchaku import NunchakuQwenImageTransformer2DModel
except ImportError as e:
    raise RuntimeError("nunchaku is required ... but it is not installed or failed to import.") from e
```

`raise ... from e` 将原始 `ImportError` 作为上下文链上，便于调试，同时用户看到的是
可操作的提示。在 NVIDIA 上该路径与之前完全一致（`try` 第一行即导入成功）。

### 4.5 验证结果（AMD 虚拟测试套件）

由于用户无法在本地 AMD 硬件上测试，虚拟测试套件通过安装 `sys.meta_path` 钩子
（对任何 `nunchaku` 导入抛 `ImportError`）来模拟 AMD 环境，然后像 ComfyUI 一样
重新导入包。

| 检查项 | AMD 模拟（屏蔽 nunchaku） | 正常（存在 nunchaku） |
|---|---|---|
| `_NUNCHAKU_AVAILABLE` | `False` | `True` |
| 注册节点 | **2**（`Krea2ControlNetLoraLoader`、`NunchakuQwenImageDiffsynthControlnet`） | **9**（全部，与之前一致） |
| 显示名称 | 2（无 Nunchaku 名称） | 9 |
| `nunchaku_code.lora_qwen` 导入 | OK，`_NUNCHAKU_AVAILABLE=False` | OK |
| 转换器助手 | 抛 `RuntimeError` | 正常工作 |
| `wrappers.*` 导入 | OK，`_NUNCHAKU_AVAILABLE=False` | OK |
| `_classify_controlnet_target` | 全部 5 条路由通过（zimage / nunchaku_qwenimage / qwenimage_standard / krea2 / unknown） | 相同 |
| Krea2 depth/openpose 判定 | 通过 | 通过 |
| 语法检查（9 个修改文件） | ALL OK | ALL OK |

**总计：50/50 全部通过。** 该套件在开发中还发现了一个真实缺陷：AMD 下
`NODE_DISPLAY_NAME_MAPPINGS` 仍残留硬编码的 Nunchaku 条目（已由 4.1 的显示名称
门控修复，提交 `6f1c2ff`）。

### 4.6 行为总结

- **AMD/ROCm**：依赖 nunchaku 的节点不注册；Krea2 ControlNet 节点可用。
  启动日志输出 `[ROCm/AMD] nunchaku is not available...`。
- **NVIDIA**：与 v2.5.5 完全一致（9 个节点）。
- **旧工作流**：引用已禁用节点时得到清晰的 `RuntimeError`
  （"nunchaku is required..."），而非晦涩的 `ImportError`。
